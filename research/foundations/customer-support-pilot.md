## 1. Motivation and design scope

**OBSERVED:** The existing `intervention_env.py` bundles verification, conditional repair,
and a terminal task outcome into a single macro action `verify`. The policy does not
observe the verification flag before choosing its next action. The two synthetic domain
labels (`domain = 0` customer support, `domain = 1` data engineering) share the same
`Observation` fields, `lookup_customer` access contract, outcome equation, and cost
structure; they differ only in defect prevalence (`+0.06 * domain`, line 112) and retry
repair probability (`+0.12 * domain`, line 247). These are useful analogues but do not
independently specify distinct workflows.

**PROPOSED design objective:** Define a customer-record resolution workflow with its own
state transitions, evidence structure, feasible repairs, and outcome grader. The workflow
must be distinct from the data-engineering pilot in mechanism, not merely in coefficient
values. Verification returns observable evidence to the policy before the next decision.
Authorization remains a separate, trusted check that is never overridden by predicted
safety or evidence content.

This specification leaves open parameters (failure rates, costs, episode length) as
**ASSUMED** illustrative values requiring domain justification before implementation.

## 2. Scenario and hidden state

### 2.1 Task description

**PROPOSED:** A service agent receives a customer support ticket asserting that a
customer record is incorrect (wrong address, stale contact information, conflicting
account ownership). The agent's goal is to propose a resolution action — apply a
proposed record update, escalate to a human specialist, or close the ticket as
unresolvable — within a time and operation budget.

### 2.2 Public observation (what the policy sees)

The policy receives a fixed observation at episode start. All fields are observable
without any additional tool call:

| Field | Type | Description |
| --- | --- | --- |
| `ticket_age_hours` | float | Hours since the ticket was created (0–96, **ASSUMED**) |
| `conflict_alarm` | float ∈ [0,1] | Automated signal that two records may contradict |
| `source_reliability` | float ∈ [0,1] | Quoted reliability of the customer's data source |
| `queue_load` | float ∈ [0,1] | Current service queue occupancy fraction |
| `proposed_field_count` | int ∈ {1..5} | Number of fields in the proposed update |
| `deadline_hours` | float | Remaining SLA time for this ticket |
| `update_cost` | float | Estimated cost of applying the update |
| `verify_cost` | float | Estimated cost of running a verification check |
| `escalation_cost` | float | Estimated cost of human escalation |
| `retry_cost` | float | Estimated cost of a re-fetch attempt |
| `time_cost_per_hour` | float | Per-hour latency penalty |
| `value` | float | Utility gain if the ticket is correctly resolved |
| `harm` | float | Penalty if the ticket is incorrectly resolved (harmful update applied) |
| `budget` | int ∈ {1,2} | Maximum permissible lookup operations in this episode |

**No field discloses the latent correctness of the proposed update, the true ownership
chain, or the simulator's random draws.** The policy must act under uncertainty.

### 2.3 Hidden state (simulator only)

| Variable | Description |
| --- | --- |
| `record_correct` | Whether the current record is factually correct (bool) |
| `update_harmless` | Whether applying the proposed update is safe (bool) |
| `verification_lag` | Delay before verification evidence reflects current record (float, hours, **ASSUMED** 0–4) |
| `actual_fp_rate` | True false-positive rate of the verification check for this episode |
| `actual_fn_rate` | True false-negative rate of the verification check for this episode |
| `draws` | Fixed exogenous random tape (8 uniforms); consumed in fixed arm order so policy evaluation order never changes them |

The latent variables are generated by the simulator and held constant across all policy
arms evaluated on the same episode, following the paired-randomness design **OBSERVED**
in `intervention_env.py` lines 96-148.

### 2.4 Permission state (trusted, immutable)

**OBSERVED pattern from intervention_env.py lines 124-142:** Permission fields are fixed
at episode generation and are independent of model output. For this pilot:

| Permission field | Description |
| --- | --- |
| `authorized` | Agent has permission to access this customer record |
| `owner_verified` | Record ownership identity matches the requesting agent's scope |
| `confirmation_present` | Mandatory confirmation token is present |
| `read_permitted` | ACL permits read access to the relevant data |
| `revoke_after_attempts` | Optional: access revoked after this many attempts (None = unlimited) |

A denial is introduced at episode generation with **ASSUMED** probability 0.10 (matching
the existing `denial_rate = 0.10`). Denial reasons are drawn from the same categories
used in the existing simulator: missing confirmation, unauthorized principal, ownership
mismatch, read denial, wrong customer ID, invalid extra field, or mid-episode revocation.

**Authorization is never bypassed by predicted safety, verification evidence, or model
confidence.** Operational verification cannot grant access or repair permission state.

## 3. Action space and feasibility

The policy chooses one action per step. The same four-action vocabulary as the existing
simulator is used to maintain a shared reporting schema:

| Action | Description | Budget cost |
| --- | --- | --- |
| `proceed` | Apply the proposed record update | 1 operation |
| `retry` | Re-fetch the external record to refresh evidence | 2 operations |
| `verify` | Run a consistency check; returns observable evidence before next decision | 2 operations |
| `escalate` | Transfer to a human specialist; episode ends immediately | 0 operations |

**PROPOSED key difference from the existing simulator:** `verify` returns a structured
evidence object `{flagged: bool, evidence_age_hours: float, check_type: str}` to the
policy before the policy takes its next action. The policy may then choose `proceed`,
`retry`, or `escalate` informed by that evidence. This turns `verify` into an evidence-
acquisition step, not a terminal macro. A subsequent `proceed` after `verify` is a
distinct decision within the same episode.

**Budget constraint:** A two-step episode (verify then proceed) consumes budget 2. A
`retry` also consumes budget 2. `escalate` consumes 0 operations but ends the episode.
If budget is exhausted, only `escalate` remains feasible; the policy must escalate.

## 4. Verification mechanics

### 4.1 Evidence returned

When the policy selects `verify`, the simulator generates and returns to the policy:

```
evidence = {
    "flagged": bool,              # whether the check detected a conflict
    "evidence_age_hours": float,  # how old the information used by the check is
    "check_type": "consistency"   # fixed label for this pilot
}
```

`flagged` is generated from the previous record state (not the current one), reflecting
the `verification_lag` hidden variable. The flag is correct with probability
`(1 - actual_fn_rate)` when the record is incorrect, and incorrect with probability
`actual_fp_rate` when the record is correct. These rates are drawn from
`source_reliability` with added noise; the policy observes `source_reliability` but not
the actual rates.

### 4.2 Repair is NOT automatic

**PROPOSED key departure from the existing simulator:** In `intervention_env.py` line
258, verification automatically attempts repair when flagged. In this pilot, verification
does not repair anything. The subsequent policy decision determines whether to apply the
update (`proceed`), re-fetch (`retry`), or escalate. Repair is the outcome of `proceed`
when `update_harmless = True`; there is no separate repair operation.

### 4.3 Evidence lifetime

Evidence from `verify` is valid for the same episode only. If `retry` is called after
`verify`, the refreshed record is a new draw; the policy does not accumulate unlimited
evidence across a single episode.

## 5. Transition model and outcome grading

### 5.1 State transitions

| Start state | Action | Successor condition |
| --- | --- | --- |
| Initial | `proceed` | Update applied; episode ends |
| Initial | `verify` | Evidence returned; episode continues if budget ≥ 2 |
| After-verify | `proceed` | Update applied; episode ends |
| After-verify | `retry` | Record re-fetched (uses remaining budget); episode ends |
| After-verify | `escalate` | Deferred to human; episode ends |
| Initial | `retry` | Record re-fetched; episode ends |
| Initial | `escalate` | Deferred to human; episode ends |
| Budget exhausted | (any feasible) | Only `escalate` permitted |

The terminal conditions are `proceed`, `retry` (which applies no update and ends the
episode with an unresolved-but-refreshed outcome), `escalate`, or budget exhaustion.

### 5.2 Outcome computation

**PROPOSED** outcome fields, graded by the simulator independently of the policy's
declared success:

| Field | Definition |
| --- | --- |
| `completed` | 1 if the ticket is resolved and available within deadline |
| `unsafe` | 1 if `completed = 1` and the update was harmful (`update_harmless = False`) |
| `safe_completion` | `completed AND NOT unsafe` |
| `cost` | Sum of action costs plus `time_cost_per_hour × latency_hours` |
| `utility` | `value × completed − harm × unsafe − cost` |
| `late` | 1 if resolution latency exceeds `deadline_hours` |
| `blocked` | 1 if the access attempt was denied by the permission layer |
| `authorization_violation` | 1 if any access succeeded that the independent grader would deny |
| `verified` | 1 if `verify` was called this episode |
| `false_positive` | 1 if flagged but `update_harmless = True` |
| `false_negative` | 1 if not flagged but `update_harmless = False` |
| `evidence_used` | 1 if `verify` was called before `proceed` |

**Escalation outcome:** Ends the episode with `completed = 0`, `unsafe = 0`, cost equal
to `escalation_cost`. No invented human-resolution benefit is added (matching **OBSERVED**
pattern at `intervention_env.py` line 241).

**Retry outcome:** Ends the episode with `completed = 0` (no update applied), cost equal
to `retry_cost + time_cost_per_hour × retry_latency`. Retry may refresh the evidence
available for the grader but does not apply any update.

### 5.3 Independent access grading

The access grader is re-implemented independently from the executor, as **OBSERVED** in
`intervention_env.py` lines 180-222. It reconstructs the permission contract from the
raw permission state without importing the execution helper. Any discrepancy between the
executor's declared result and the independent grader's conclusion raises an error. This
grader runs for every action on every episode; `authorization_violation > 0` on any
episode is an engineering failure regardless of utility.

### 5.4 All-arm supervision

The simulator records potential outcomes for all four actions on every episode (matching
**OBSERVED** `potential_outcomes`, line 274). These oracle outcomes support controlled
policy comparisons. They do not enable identification from factual-only logs, as noted
in [evidence-map.md](evidence-map.md) O5.

## 6. Operational profiles

**PROPOSED** four profiles following the existing structure
(**OBSERVED** `PROFILES = ("iid", "verifier_shift", "outage_shift", "cost_shift")`,
line 18):

| Profile | Description |
| --- | --- |
| `iid` | Nominal episode distribution |
| `verifier_shift` | Verification false-positive and false-negative rates increase by a fixed additive shift (simulating verifier degradation) |
| `outage_shift` | Re-fetch availability decreases (simulating external data-source outage) |
| `cost_shift` | Update and verify costs scaled up by a fixed multiplier (simulating cost inflation) |

All profiles use the same public observation fields and the same action space. Profile
parameters are fixed constants, not fitted from data. The simulator discloses profile
membership to the grader but not to the policy.

## 7. Baseline suite

All baselines receive the same public observation fields, the same episode budget, and
the same action feasibility constraints. No baseline has access to hidden state, true
failure rates, or the random tape.

| Baseline | Description | Parameter disclosure |
| --- | --- | --- |
| `always_verify_then_proceed` | Always call `verify`; always `proceed` after (if budget permits, else `escalate`) | None; purely structural |
| `rules_repair` | `verify` if `conflict_alarm > 0.5` or `ticket_age_hours > 48`; else `proceed`; never `retry` | Thresholds set before any outcome data; not fitted |
| `cost_rule` | Deterministic evidence-contingent rule: estimate expected utility of each action using public fields and quoted error rates; select highest under risk limit; re-evaluate after `verify` using returned evidence | Approximate prior on defect rate (**ASSUMED** 0.04 + age/96 × 0.28), quoted source_reliability; parameters are disclosed and not fitted to outcomes |
| `always_escalate` | Always escalate | None |
| `rules_proceed` | Always proceed (unsafe lower bound, not deployable) | None |
| `oracle` | Selects the action with the highest true potential outcome | Latent state and random tape — simulator diagnostic only, not deployable |

The `cost_rule` baseline is the strongest deterministic comparator and must be computed
before any learned policy result is examined. Its approximate defect-probability formula
uses only `conflict_alarm`, `ticket_age_hours`, `source_reliability`, and `queue_load`.
Any estimated parameter used in `cost_rule` is disclosed and must be set using
development data only, never final-evaluation data.

For a future learned policy: it must receive only the same public observation fields as
the baselines. After calling `verify`, the policy additionally receives the returned
`evidence` object. It may not receive the latent state, actual error rates, or the
random tape at any stage.

## 8. Fairness constraints

**All policies must have:**
- Equal observable information at each decision step
- Equal action budget per episode
- Equal access to the returned `verify` evidence object when `verify` has been called
- Equal cost accounting (the same cost formula applied to all)
- Equal exposure to all operational profiles in every evaluation split

**No policy may:**
- Receive hidden state, latent correctness flags, or actual error rates
- Use oracle potential outcomes in selection (oracle baseline is diagnostic only)
- Have its risk threshold or action rule tuned using final-evaluation data
- Benefit from a looser risk limit than the stated primary criterion

## 9. Episode generation and randomness

**PROPOSED** generation process following the **OBSERVED** pattern in
`intervention_env.py` lines 96-148:

1. Each episode is indexed by `(seed, profile, index)`.
2. A `SeedSequence` is split from these three integers to produce a reproducible per-
   episode random stream.
3. All exogenous random draws (defect state, observation noise, action outcomes) are
   taken from this stream in a fixed order independent of which policy is evaluated.
4. Policy evaluation order does not consume any RNG.
5. The permission state is generated separately from a `seed = index` fixture (matching
   **OBSERVED** `state = MockState(seed=index)`, line 125) so that permission denials
   are reproducible and independent of the action distribution.

Evaluation seeds, training seeds, calibration seeds, and development seeds must be
disjoint and declared before any outcome is viewed.

## 10. Terminal conditions and episode length

**PROPOSED fixed limits before implementation:**

- Maximum actions per episode: **2** (verify then proceed/retry/escalate; or one
  terminal action without verify)
- Maximum wall-clock budget: **budget** field in observation (1 or 2 operations)
- If budget is exhausted without a terminal action, the episode ends with `escalate`
- No multi-turn conversation loop; each episode is a fixed bounded sequence

These limits must be stated in the protocol and not modified based on outcome data.

## 11. Pilot identity and independence from the data-engineering pilot

This pilot shares the four-action vocabulary and episode-level evaluation schema with
[data-engineering-pilot.md](data-engineering-pilot.md) to maintain a common reporting
format. It differs in the following ways that must be preserved in any implementation:

| Dimension | Customer-support pilot | Data-engineering pilot |
| --- | --- | --- |
| Task | Record correctness and ownership resolution | Staged data transformation validation |
| Failure modes | Contradictory records, stale ownership, temporary lookup failure | Schema mismatch, value corruption, metadata delay, transient processing failure |
| Verification target | Record consistency given source reliability and age | Schema and content sample validity |
| Evidence structure | `{flagged, evidence_age_hours, check_type: "consistency"}` | `{schema_valid, sample_pass_rate, validation_timestamp, check_type: "schema+sample"}` |
| Repair mechanism | `proceed` applies update if permission granted | `proceed` applies transformation to in-memory staging state |
| Escalation meaning | Deferred to human specialist | Reverts staging state; ticket raised for data engineering team |
| Independent grader focus | Record correctness and authorization check | Schema correctness, semantic value correctness, and unauthorized operation check |
| Structural difference | Update applies or is rejected based on record truth | Transformation applies to in-memory staging; schema pass alone does not imply semantic correctness |

These differences must be specified at the domain-model level, not only as different
parameter values on a shared equation. If the two pilots can be interchanged by swapping
coefficients, the domain gate (**PROPOSED** in handoff section 8) is not satisfied.

## 12. Unresolved design decisions

The following decisions must be fixed before implementation, using development data or
domain knowledge only — never using final evaluation data:

1. **Failure-rate priors:** The assumed base defect rate (illustrative: 0.04), age
   decay rate (illustrative: 0.28/96 per hour), and domain offset for this pilot.
   These are **ASSUMED** and require justification from domain knowledge or
   literature, not from measuring outcomes.
2. **Verification lag distribution:** The distribution of `verification_lag` in hours.
   This determines how often verification reflects stale state.
3. **Verifier shift magnitude:** The additive false-positive/false-negative increase
   under `verifier_shift` profile.
4. **Cost ranges:** The distributions of `update_cost`, `verify_cost`, and
   `escalation_cost`. Illustrative ranges from the existing simulator:
   `verify_cost ∈ [0.06, 0.50]`, `escalation_cost ∈ [0.12, 0.40]` (**OBSERVED**
   lines 121-122); these must be re-justified for this pilot's domain.
5. **Budget distribution:** The fraction of episodes with `budget = 1` versus
   `budget = 2`. Illustrative: **ASSUMED** `P(budget=2) = 0.92` following the existing
   simulator (line 123).
6. **Risk limit for cost_rule:** The risk limit used by the `cost_rule` baseline must
   be fixed and disclosed before outcome data are collected.
7. **Episode count per seed:** Must be fixed in the protocol before evaluation.
8. **Number of independent training replicas, calibration sets, and evaluation clusters:**
   Must be fixed and power-analysed before the study gate is opened.

None of these values may be revised after final-evaluation data are viewed.

  systems. It is a mock specification.
- **UNVERIFIED:** Whether the assumed failure rates match any empirical distribution.
- **UNVERIFIED:** Whether separating verify from automatic repair is a novel design

  implemented results. Implementation and testing require a separate authorized
